## Implemented transactions

- `register_app_guest(uuid,jsonb)` accepts the eight required profile fields plus the explicitly allowed optional household fields, requires personal-contact permission, and derives Auth ID/email from the current nonanonymous, nondeleted, nonbanned account. It stores a pending guest-register row, initial Central-date follow-up due two days later, a welcome job and an Office follow-up task on first registration. It never creates or changes a membership/contact/history record automatically. Updating a profile preserves its staff metadata and existing contact link.
- `submit_app_prayer(uuid,jsonb)` accepts only display name, request text and optional contact text. It creates a private Office prayer with immutable app provenance, `staff_only` sharing and no sharing approval. Prayer-only submission creates a private care task and generic staff notices, with no guest, person or welcome email; prayer content never enters either email outbox.
- `get_my_app_connection()` retains its public signature and returns only the account's own public profile, including self-reported visit fields. It omits staff notes, recorded visit, assignments and review metadata. Its private implementation uses the new app-account rule, without weakening staff eligibility.
- `update_guest_followup(uuid,integer,jsonb)` is admin/editor-only, with a locked row and independent expected `staff_version`. It edits only recorded visit, follow-up date/status and welcome owner. It cannot change profile version, identity/review information or membership.
- `direct_intake_readiness()` is staff-only and returns `{available:true,version:1,tasks:true,routes:true}`. This is the Office UI's positive capability check; missing capability on the historical eight baseline keeps the new editor fields unavailable while preserving old Office operations.

Guest profile JSON requires `first_name`, `last_name`, `phone`, `preferred_contact`, `contact_permission`, `sunday_school`, `visit_status`, `first_visit_on`. Optional text may be null where defined; `last_name` is a string, including empty. A `not_yet` visit has no first-visit date. Prayer JSON requires `request_text`; omitted optional fields normalize to a private fallback display name and null contact. Dates are exact valid ISO dates. Extra keys, wrong types, consent failures and invalid dates return fixed errors.

Optional own-profile fields are `birth_date`, `membership_status`, `address_line1`, `address_line2`, `city`, `state_region`, `postal_code`, and `family_members`. Omitted fields preserve saved values on an existing profile, so an older client cannot erase newer household details. Explicit null clears a nullable date/address; an empty family array clears the household list. Membership is self-reported (`member`, `regular_attender`, `guest`, `exploring`, `unsure`) and never creates a membership link. New profiles default to unsure and no household details.

Birthdays must be valid ISO dates no later than today's America/Chicago date. Address lines allow 160 characters each; city/state 100; postal code 20. Family arrays allow 20 entries, with required first name up to 100 and relationship (`spouse`, `child`, `parent`, `guardian`, `other`), optional last name up to 100 and optional nonfuture birthday. Nested extra keys and invalid types are rejected. These private details are visible only through the own-profile projection and eligible Office access. Neither email outbox receives addresses, birthdays or child details.

Each account/operation/request UUID records a hash of normalized whitelisted JSON and its original receipt. Optional profile keys are hashed only when submitted, preserving retry identity even when a newer client later changes other optional fields. Identical replays return that receipt; changed payloads conflict (`40001`). Account-row locking serializes receipt and quota checks. New guest requests are limited to 10/hour; prayers to 10/hour and 50/rolling 24 hours. Valid same-key retries are checked before quotas. A saved receipt confirms a committed record, not email delivery or staff contact.

## Welcome outbox contract

Six private tables hold request receipts, welcome jobs, registration-to-job links, the shared UTC-day quota, routing defaults and staff notice jobs. All have RLS; PUBLIC, anon, authenticated and service_role have no direct table privileges. Narrow private definers sit behind public invoker wrappers. Only service_role can execute the claim/finish RPC pair.

`claim_app_welcome_jobs(scope_user_id,limit)` returns an array of `id`, `lease_token`, `recipient`, `first_name`, `template_version`, `first_attempt_at`, `attempts`. The service-side dispatcher supplies scope only after authenticating the requester; a null scope is for its authorized scheduler. SQL verifies job-account eligibility and current recipient match before claiming. New jobs freeze their first name, normalized recipient and `creek-welcome-v1` template. Email deduplication can link a recreated/case-varied account's registration to the same job; it never changes the original send payload.

Claims use `FOR UPDATE SKIP LOCKED`, a 120-second lease and persisted attempt metadata before any HTTP request. One locked UTC-day counter limits new first-attempt slots to 80 across welcome emails and staff notices together; retries keep their original slot. Retry backoff starts at 60 seconds and caps at one hour. At 23 hours from the first attempt, further claims become manual-attention items. This deliberately ends before the provider's 24-hour idempotency window. The immutable v1 email builder must remain available for old v1 jobs in any later release.

`finish_app_welcome_job(id,lease_token,status,provider_id,error_code)` accepts `sent`, `retry` or `attention` only for the matching, still-valid lease. Sent is terminal; stale or expired leases return `40001`. Provider IDs must be UUIDs, and errors use the fixed allowlist shared with the dispatcher. No provider body, password, key or arbitrary error text is stored. Public register status mirrors the linked outbox. `sent` means the provider accepted the request; it is not a confirmed-delivery claim.

Existing registrations receive `attention` metadata and no retroactive email job or task. Registration updates never enqueue another welcome. Staff must decide any follow-up for earlier records separately. This preserves original records instead of interpreting this deployment as authorization for old mail.

## Durable Office actions and staff notices

Every first guest registration saves one `guest_followup` task, due two Central calendar days later. Every new prayer saves one `prayer_care` task, due that Central date. Source, task, initial email jobs and receipt commit together; a task failure rolls the submission back. A replay cannot duplicate tasks. Existing registration updates retain their task. No submission automatically joins membership or modifies a historical ledger.

`app_submission_tasks` is readable by eligible admins/editors only. Its two new policies protect task reads and task audit entries while preserving all 54 prior policy definitions. There are 56 policies after this draft. Direct task writes are revoked; `update_intake_task(id,version,changes)` accepts only non-null valid `due_on`, recognized `status`, and an eligible staff UUID or null assignment. Completion timestamps/actor, sources, routing and email status are server-owned. Expected-version conflicts return `40001`. Audit records contain action/source IDs, never submitted prayer bodies.

`get_intake_settings()` returns version 1, the two route rows, and minimal existing eligible admin/editor IDs and email labels for the private selector. It creates no accounts, roles or invitations. `set_intake_route(kind,version,assigned_staff_user_id)` is admin-only and affects future submissions only. Null means the Office queue; an unavailable configured staff member falls back to the Office queue when a task is created. Existing tasks keep their own assignment until staff explicitly edit them. Deacons can appear only after separately approved Office access; no roster or email is inferred from submitted forms.

Each task queues generic notices to its current eligible assignee, or to eligible administrators for the Office queue. The recipient comes from approved Auth/staff rows. Guest fields and the free-text welcome owner cannot choose recipients. Jobs freeze `creek-office-notice-v1` and the recipient, deduplicated by task and normalized email. Reassignment queues a newly targeted recipient at most once. Prior recipients whose jobs are still queued are excluded when next claimed; already accepted or in-flight mail cannot be recalled. An attention job requires review, including a former recipient later selected again; it is never silently reset.

`claim_app_staff_notice_jobs(scope_user_id,limit)` returns `id`, `lease_token`, `recipient`, `task_id`, `task_kind`, `template_version`, `first_attempt_at`, `attempts`. Scope is the submitting account, not the recipient. SQL rechecks both the submitting account and current approved recipient/route before claim. No guest name, guest email or prayer text enters this generic notice payload. `finish_app_staff_notice_job(id,lease_token,status,provider_id,error_code)` shares the welcome finish contract, 120-second leases, fixed errors, bounded retry backoff and 23-hour cutoff. Both RPC pairs are service-only. The worker must distinguish welcome outcomes from staff-notice outcomes.

Task `notification_status` summarizes the current recipients' jobs. `sent` requires all current targets' requests to be accepted by the provider, not delivered or read. Missing/ineligible current recipients or stopped jobs require attention. A later role change is rechecked during a subsequent claim; the displayed saved status is not a continuous delivery/eligibility monitor.

## Separate scheduler extension prerequisite

The CLI also generated `20260909215330_direct_intake_dispatch_extensions.sql`. This separately applied migration enables `pg_cron` with schema `pg_catalog` and `pg_net` with schema `extensions`, following the official [Cron install](https://supabase.com/docs/guides/cron/install) and [extension example](https://supabase.com/docs/guides/ai/automatic-embeddings). These extensions maintain their own `cron`/`net` objects. The file creates no schedule, Vault secret or HTTP request and changes no existing extension version. Both must be available on the exact hosted target, with existing namespace/version and function privileges checked after activation. PGlite cannot execute these infrastructure extensions, so the 34 tests do not claim that acceptance.

The separately reviewed dispatcher activation must still provision its server-only scheduler secret and durable schedule. The browser's immediate dispatch is a convenience; it is not the reliable retry mechanism. The extension file alone does not make pending jobs run.
